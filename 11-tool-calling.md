# 11. Вызов инструментов: шаблоны чата, грамматики, JSON Schema

> **Зачем эта глава.** Модель не «вызывает функции» — она пишет текст. Весь вызов инструментов держится на договорённости: шаблоне чата, формате сообщений и парсере. Если договорённость нарушена, агент ломается, даже когда модель умная.

## 11.1 Модель пишет текст, сервер разбирает

Механика вызова инструментов:

1. Приложение описывает доступные инструменты: имя, назначение, параметры.
2. Сервер подставляет эти описания в промпт через **шаблон чата** (chat template) в формате, на котором модель обучалась.
3. Модель отвечает специальной разметкой, например:

```
<tool_call>{"name": "get_weather", "arguments": {"city": "Москва"}}</tool_call>
```

4. Сервер парсит разметку и отдаёт приложению стандартные OpenAI-совместимые `tool_calls`.
5. Приложение выполняет инструмент и отправляет результат обратно сообщением с ролью `tool`.

Важно: **никакого встроенного механизма вызова у модели нет**. Есть только обучение на текстовых форматах и парсер на сервере.

## 11.2 Шаблон чата

**Chat template** — правило, как роли (`system`, `user`, `assistant`, `tool`), сообщения и описания инструментов превращаются в последовательность токенов. Он хранится в метаданных модели (в GGUF — внутри файла) и обычно написан на Jinja.

Пример упрощённо:

```
<|system|>
Ты — помощник. Доступные инструменты: ...
<|user|>
Какая погода в Москве?
<|assistant|>
<tool_call>...
```

Что ломается, если шаблон неправильный:

- модель не понимает, где заканчивается сообщение;
- описания инструментов попадают не туда;
- специальные токены превращаются в обычный текст;
- модель отвечает в формате другой модели.

Поэтому флаг `--jinja` (использовать шаблон из файла модели) важен: без него сервер может применить упрощённый формат, и tool calling перестанет работать.

## 11.3 Форматы tool calls

Разные семейства моделей обучены на разных форматах:

- JSON в специальных токенах;
- XML-подобные теги;
- отдельные маркеры ролей;
- массивы вызовов для параллельных инструментов.

Сервер знает формат благодаря шаблону и парсеру. Если вы меняете модель, проверьте:

- совместим ли шаблон с вашим клиентом;
- поддерживает ли сервер парсинг именно этого формата;
- как выглядят параллельные вызовы;
- что происходит при ошибке парсинга.

Универсального формата нет; «OpenAI-совместимость» — это про API, а не про внутренний текст модели.

## 11.4 Грамматики и JSON Schema

Даже хорошая модель иногда ломает JSON. Есть жёсткое решение: **constrained decoding** (ограниченное декодирование).

Идея: на каждом шаге парсер знает, какие токены допустимы в текущем состоянии грамматики, и **обнуляет логиты** всех остальных. Тогда синтаксически неверный JSON физически невозможен.

В llama.cpp для этого есть:

- **GBNF** — грамматика в нотации, похожей на BNF;
- `--grammar` и `--grammar-file`;
- `response_format: {"type": "json_schema", ...}` — JSON Schema, преобразованная в грамматику;
- серверный `--json-schema`.

Другие реализации:

- **Outlines** — компиляция регулярных выражений и JSON Schema в маски;
- **XGrammar** — быстрый движок структурированной генерации;
- в vLLM — strict tool schema и guided decoding.

Что гарантирует грамматика:

- синтаксис (валидный JSON, нужные поля, типы);
- отсутствие «болтовни» вокруг JSON.

Чего она **не** гарантирует:

- правильность значений (модель может поставить выдуманное число);
- соответствие схеме по смыслу (например, «дата» может быть неверной);
- что модель выберет правильный инструмент;
- что аргументы будут полными по смыслу, а не только по форме.

Грамматика — это ремень безопасности, а не замена проверке.

## 11.5 Производительность грамматик

Ограниченное декодирование добавляет накладные расходы:

- на каждом шаге нужно вычислить маску допустимых токенов;
- сложные схемы (глубокая вложенность, большие перечисления) замедляют;
- некоторые реализации кэшируют состояния, другие пересчитывают.

На практике для типичной схемы на 10–20 полей overhead невелик, но на очень больших схемах может быть заметен. Если скорость критична, упрощайте схему.

## 11.6 Дизайн инструментов

Хорошая схема повышает надёжность сильнее, чем любая магия промптинга.

Правила:

1. **Мало инструментов.** 5–15 лучше, чем 50. Каждый инструмент — это текст в промпте и шанс ошибиться.
2. **Ясные имена и описания.** Модель выбирает по описанию, а не по вашему замыслу.
3. **Плоские аргументы.** Глубокая вложенность увеличивает число ошибок.
4. **Enums вместо свободного текста.** Если значение из фиксированного набора — перечислите его.
5. **Обязательные поля — действительно обязательные.** Не делайте всё optional.
6. **Ошибки как данные.** Возвращайте структурированную ошибку, чтобы модель могла исправиться.
7. **Ограничивайте размер результата.** Огромный вывод инструмента съедает контекст и ломает кэш.

## 11.7 Цикл агента

Типичный цикл:

```
while not done and steps < max_steps:
    response = model(messages, tools)
    if response has tool_calls:
        for call in tool_calls:
            result = execute(call)
            messages.append(tool_result)
    else:
        done
```

Проблемы, которые надо предусмотреть:

- **модель не вызывает `finish`** и крутится до лимита;
- **повторяет один и тот же вызов**;
- **вызывает несуществующий инструмент**;
- **передаёт битые аргументы**;
- **теряет цель** на длинной истории;
- **переполняет контекст** результатами инструментов.

Лечения:

- явное условие завершения и инструмент `finish`;
- лимит шагов и бюджета токенов;
- валидация аргументов на стороне приложения;
- напоминания о формате при ошибке;
- сжатие или суммаризация истории (осторожно с кэшем промпта);
- грамматика для аргументов.

## 11.8 Безопасность

Вызов инструментов — это исполнение действий. Даже локальная модель может:

- выполнить опасную команду, если инструмент ей это позволяет;
- передать данные из документа в нежелательное место;
- поддаться **prompt injection** в тексте документа или результате инструмента.

Правила:

- минимальные права у инструментов;
- подтверждение опасных действий человеком;
- изоляция файловой системы и сети;
- валидация входных данных, а не доверие модели;
- логирование вызовов.

Локальность модели не делает её безопасной: она лишь убирает утечку в облако.

## 11.9 Как измерять качество вызова инструментов

Метрики:

- доля синтаксически валидных вызовов;
- доля вызовов с правильным инструментом;
- доля с правильными аргументами;
- среднее число шагов до завершения;
- доля незавершённых задач;
- доля повторных/зацикленных вызовов.

Прогоняйте на реальных сценариях, а не на одном примере. Полезны публичные бенчмарки (например, BFCL), но они не заменяют ваш домен.

## Ключевые идеи

- Вызов инструментов — это текст плюс парсер, а не встроенная функция модели.
- Шаблон чата определяет формат; без правильного шаблона tool calling ломается.
- Грамматика и JSON Schema гарантируют синтаксис, но не смысл.
- Хороший дизайн инструментов важнее сложных промптов.
- Агентский цикл нужно ограничивать шагами, бюджетом и проверкой аргументов.

## Проверь себя

1. Почему модель «не знает», что у неё есть инструменты, без шаблона чата?
2. Что гарантирует грамматика JSON и чего она не гарантирует?
3. Почему 50 инструментов хуже 10?
4. Как prompt injection может повлиять на агента с инструментами?
5. Какую метрику вы бы смотрели в первую очередь при отладке tool calling?

## Ответы

1. Описания инструментов и формат вызова передаются модели только через промпт, собранный шаблоном. Без шаблона модель не получает ни описаний, ни разметки, на которой обучена.
2. Гарантирует синтаксис: валидный JSON, нужные поля, типы. Не гарантирует правильность значений, выбор инструмента и смысловое соответствие.
3. Каждый инструмент занимает место в промпте и увеличивает число вариантов. Модели труднее выбрать, растёт вероятность ошибки и стоимость prefill.
4. Вредоносный текст в документе или результате инструмента может убедить модель вызвать инструмент с опасными аргументами. Модель не отличает данные от инструкций, если это не предусмотрено дизайном.
5. Долю валидных вызовов с правильным инструментом и аргументами, а также долю задач, завершённых без зацикливания. Синтаксическая валидность без правильного инструмента бесполезна.
